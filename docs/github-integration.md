# GitHub integration

## What Community Build can and cannot do

| Capability | Community Build | Developer Edition+ |
| --- | --- | --- |
| Analyze the main branch | Yes | Yes |
| Quality gate via API / CI | Yes | Yes |
| Import projects from GitHub | Yes | Yes |
| Sign in with GitHub | Yes | Yes |
| Pull request decoration | No | Yes |
| Multi-branch analysis | No | Yes |

If you need PR feedback inside GitHub with Community Build, a common pattern is: SonarQube as the quality gate on main (this repo's [scanner workflow](../examples/github-actions/)), plus a lightweight scanner such as Semgrep running directly on pull requests.

## Sign in with GitHub (recommended for orgs)

1. In your GitHub org, create a GitHub App: Settings > Developer settings > GitHub Apps.
   - Homepage URL: `https://sonar.example.com`
   - Callback URL: `https://sonar.example.com`
   - Permissions: read-only access to Organization members and Email addresses
   - Disable webhooks and install the App on your organization.
   - For repository import, configure the separate DevOps platform integration following the [official GitHub App instructions](https://docs.sonarsource.com/sonarqube-community-build/devops-platform-integration/github-integration/setting-up-at-global-level/setting-up-github-app).
2. In SonarQube: Administration > Configuration > Authentication > GitHub, fill in the App ID, client ID, client secret, private key and your organization name.
3. Enable "Allow users to sign up" restricted to your organization.

The module already sets `SONAR_CORE_SERVERBASEURL`, which is required for the OAuth callback to work.

## Analyzing repositories

1. Create the project in SonarQube (manually or through the GitHub import).
2. Generate a project analysis token.
3. Add the [scanner workflow](../examples/github-actions/sonarqube-scan.yml) to the repository with `SONAR_HOST_URL` as a variable and `SONAR_TOKEN` as a secret. Share `SONAR_HOST_URL` at organization level; store each project token in its repository secret named `SONAR_TOKEN`. A single organization secret with that name cannot hold different tokens for each repository.

## Webhooks

To notify external systems when analysis completes, configure webhooks in SonarQube under Administration > Configuration > Webhooks. Outbound HTTPS from the instance is allowed by default.

## Token hygiene

- One analysis token per project, stored only in GitHub secrets.
- Rotate tokens when people leave the team.
- Never use the admin account for analysis.

## Organization rollout

Start with one representative repository. Inventory languages, default branch names, monorepos and existing test/coverage commands before rolling out the workflow. Set project visibility to private and review permission templates; restricting sign-in alone does not define project access.

The example uses the repository default branch and `SONAR_PROJECT_KEY`. Configure that variable per repository and the URL at organization level. Java/Maven, Gradle and .NET projects need their dedicated scanner/build sequence; coverage reports must be generated by your tests before scanning. Set exclusions and coverage report paths in each repository's `sonar-project.properties`.

A failed Quality Gate on a push happens after the commit is integrated. This Community workflow does not provide a pre-merge PR gate. Native branch/PR analysis requires a suitable paid edition; select that edition before designing required PR checks.

See the [current authentication instructions](https://docs.sonarsource.com/sonarqube-community-build/instance-administration/authentication/github) when registering the App for the pinned server version.
